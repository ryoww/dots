# docs の書き方

Issue 駆動開発では、Issue が `docs/` を参照し、実装が `docs/` に従い、振る舞いを変えたら同じ PR で `docs/` を直す。
docs が曖昧だと Issue も実装もぶれるため、docs の書き方を先に固定する。
この文書は、新しいリポジトリに `docs/` を敷くときと、そのあとで文書を足すときの規範。

## 目次

1. 文書の層と責務

11. 最初に敷く最小構成

## 1. 文書の層と責務

同じ事実を複数の文書に書かない。各文書は次の関心ごとだけを持ち、それ以外はリンクで参照する。

| 問い | 文書 | 書くこと | 書かないこと |
|---|---|---|---|
| 何のために・何をやらないか | `vision.md` | 対象ユーザー・責務・やること・やらないこと・判断の基準 | 個々の振る舞い・技術 |
| どう振る舞うか | `specs/<機能>.md` | 状態・振る舞い・受け入れ条件・範囲外 | 理由・ライブラリ・方式 |
| なぜそう決めたか | `decisions/D-XXXX` | 背景・決定・ほかの選択肢・根拠・影響 | 振る舞いの網羅(それは仕様) |
| まだ決まっていないか | `open-questions.md` | 問い・状態・影響・選択肢・決定へのリンク | 結論の本文 |
| どう進めるか | `workflow.md` | Issue → PR の流れ・ブランチ・マージ規約 | プロダクトの中身 |

この分け方の利点は、Issue が「仕様を書き換える」「決定を記録する」「OQ を解決する」と作業を具体的に指せること。AI にも「どこに何を書くか」を一意に指示できる。

## 2. 一次情報は 1 か所だけ

ある事実の「正」は 1 文書に置き、他の文書は再掲せずリンクする。

- `docs/README.md` に「事実 → 一次情報(正)」の表を持つ。新しい種類の事実を書き始めたら、この表に 1 行足す。
- 参照は「〜は `specs/<機能>.md` を正とする」「(`D-XXXX`)」のように、**どこが正かを文中で示す**。
- 要約して再掲したくなったら、それは表の行が足りないか、文書の責務が混ざっている合図。再掲せず、リンク先を直す。
- `README.md` に文書の一覧を置かない(`ls docs/specs/` `ls docs/decisions/` で見る)。手で持つ一覧は実ファイルとずれる。一覧表を手で保守していると、並行する PR で**同じ番号の決定が 2 件**できても気づけない。一覧ではなく `/check-docs` の採番検査で守る。

`specs/README.md` の「一覧」表だけは例外として持つ。仕様の状態を一望する価値が高いため。ただし**正は各仕様ファイルの冒頭**で、一覧はその写し。ずれは `/check-docs` が検出する。

## 3. 未確定のことの書き方

**記述にステータスの印は付けない。印が無い記述は、現時点の決定として読む。**
`[確定]` `[提案]` `[保留]` のような印は、付けた直後は意味があっても更新されず腐る。

決められないことは次の形で書く。

- 本文:「〜は**未確定**(`OQ-NNN`)」
- `open-questions.md`: 問いそのものを `OQ-NNN` で置く(形式は雛形)

本文とハブが番号で結ばれるため、どちらか一方に取り残されない。

解決したら、項目を**消さずに「解決済み」へ移し、決定 `D-XXXX` へリンクする**。結論の本文はここに書かない(決定と、反映した仕様が持つ)。
消さないのは、「あの論点はどうなった」を後から辿れるようにするため。削除方式にすると、git 履歴を掘らないと経緯が追えない。

`open-questions.md` で扱うのは**値・形式・方式といった設計の詳細**。機能を持つ / 持たないは `vision.md` で決め、ここには置かない。

AI が作業中に決められないことに当たったら、**推測で決めて進まず**、選択肢と推奨を添えて OQ に書いて尋ねる。これが Issue 駆動で AI を使うときの最重要ルール。

## 4. `vision.md` の書き方

機能を足すかどうか迷ったときの判断基準になる文書。節は次のとおり。

- **誰のためのアプリか** / **解決したいこと** … 一文ずつ。
- **責務** … このアプリが受け持つ範囲。
- **やること** … 機能のまとまりごとに箇条書き。仕様があればリンク。
- **やらないこと** … 面倒をみないこと。**理由付きの表**にする。「ここに書いたことを求める Issue は、この文書を書き換える合意がない限り受けない」と明記する。AI に「気を利かせて足される」のを防ぐ仕掛け。
- **判断の基準** … 迷ったときに優先する考え方を、優先順に番号で。

「やらないこと」と「まだ作っていない」を混ぜない。前者は `vision.md`、後者は `specs/README.md` の「予定」表。この 2 つを分けると「作らないと決めたもの」を AI が勝手に着手しなくなる。

`vision.md` を書き換えるときは理由を `decisions/` に残す。

## 5. `specs/` の書き方

1 機能 1 ファイル。ファイル名は短い英語スラッグ(`<機能>.md`)。他文書からは `specs/<機能>.md` で参照する。

冒頭のメタ行。

```markdown
- 状態: 下書き | 合意 | 実装済み
- Issue: #番号
- 関係する決定: D-XXXX、D-XXXX
```

- **下書き** … 書いている途中。未解決の項目が残っている。
- **合意** … 内容が決まり、実装してよい。受け入れ条件が確定している。
- **実装済み** … コードがこの仕様どおりに動く。受け入れ条件がすべてチェックされている。

節の構成は 目的 → 振る舞い → 受け入れ条件 → エラー・空状態 → 範囲外 → 未解決の項目。

書き方のルール。

- **目的**には `vision.md` のどの項目に当たるかを書く。vision に当たる項目が無いなら、その機能は要らないか vision が足りない。
- **振る舞い**は利用者の操作とアプリの動きを順に番号で。条件・タイミング・値は具体的に(「〈桁数〉桁の数字」「発行から〈時間〉時間」)。理由は書かず `D-XXXX` へリンクする。
- **受け入れ条件**は、人が確かめられる形で書く。テストはこの条件と対応させる。**確かめていない条件にチェックを付けない**。
- 状態を持つ機能なら、状態の表と遷移図(mermaid の `stateDiagram-v2`)を振る舞いの前に置く。
- 他の機能のルールを再掲しない。「作成すると通知が飛ぶ(`specs/<通知の機能>.md`)」のようにリンクする。
- ライブラリ名・API 名・テーブルの列名を書かない。それは決定と data-model の責務。

## 6. `decisions/` の書き方

ファイル名は `D-XXXX-英語スラッグ.md`(4 桁ゼロ埋め、連番)。形式は雛形 `_template.md`。

メタ行は 日付・決めた人・関係する Issue と PR・解決した未解決の項目・置き換える記録。節は 背景・決定・ほかの選択肢・根拠・影響。

ルール。

- **追記のみ。消さない、本文を書き換えない。** 誤字は直してよい。意味が変わる直しはしない。記録の価値は「当時どう考えたか」が残ることにある。
- **ステータス行を持たない。** `decisions/` にある記録は、置き換えの注記が無いかぎり有効な決定。「承認待ち」の段階も持たない(記録は議論が済んでから書く)。
- **覆すときは新しい記録を書く。** 新記録の「置き換える記録」に旧番号を書き、旧記録のメタ行の直後に引用ブロックで「**この記録は D-XXXX で置き換えられた。**」と何が変わったかを足す。旧記録の本文はそのまま残す。
- **「ほかの選択肢」が空の記録は作らない。** 選択肢が議論されていなければ、調べて比較してから書く。
- **「決めた人」を分けて書く。** 人の判断と AI の案を区別する(「〈依頼した人〉(依頼)。ファイルの構成は AI が案を作った」)。あとで「誰が決めたか」が問題になったとき効く。
- **「根拠」には確かめていないことも書く。** 「〜と考えているが、確かめていない」を残しておくと、あとで検証の Issue にできる。
- **採番の衝突に気をつける。** 並行する PR で同じ番号が付くことがある。記録を作るとき同番号が無いか確かめ、あとからマージする側が付け直す。`/check-docs` が重複を検査する。
- 決めきれていない論点が残るなら、記録を保留にせず OQ を起票して記録から参照する。
- 決定の結果は該当する仕様に反映する。仕様には結果だけを書き、理由はこの記録へリンクする。

## 7. `workflow.md` の位置づけ

Issue から PR までの進め方の**正**。人も AI も読む。`AGENTS.md` には要点だけを書き、丸ごと再掲しない。

ここに書くのは、Issue の立て方・ブランチ名・docs を先に書く順序・PR の形・squash merge の規約・仕様とコードをそろえる決まり。プロダクトの中身は書かない。

## 8. 補助文書

必要になってから足す。

- **`glossary.md`** … 人と AI が同じ言葉で話すための辞書。列は「用語 / 英語 / UI 表示 / 定義 / 正」。置くのは言葉そのもののこと(定義・画面での表示・文体)だけで、条件やタイミングは「正」の列が指す文書を読む。docs を書くときは「用語」列の語を使い、画面の文言を書くときは UI 表示に合わせる。
- **`data-model.md`** … 冒頭に「列・型・制約の正は〈スキーマの置き場所〉」と断り、列の一覧を再掲しない。書くのは**なぜその形か**(導出・付け替え・境界・ON DELETE の方針)だけ。ER 図は mermaid の `erDiagram` でキーだけ。
- **`setup/`** … 外部サービスの設定手順。一度しかやらない作業の記録。
- **`non-functional.md`** … 対応範囲・オフライン・エラー方針・権限・公開要件。仕様に散らばりがちな横断ルールをここに集める。

## 9. 文体と細部

- 日本語・である調。AI が書く文章も同じ。
- 「〜を正とする」「(`D-XXXX`)」で正の所在を示す。参照は `specs/<機能>.md`・`D-XXXX`・`OQ-NNN`・`vision.md`「やらないこと」の形で統一する。
- 太字は**決定の核**だけ。装飾に使わない。
- 数値・形式・期限は具体的に。「適切に」「必要に応じて」は書かない。
- Issue・PR 番号を本文に残す(「Issue #〈番号〉」「#〈番号〉で追加」)。なぜそう決めたかを GitHub に辿れる。
- 図は mermaid を優先する(差分が読める)。画像は `docs/images/` に置く。
- 文書に書く事実は、元の資料や会話にあるものだけ。無い効果・感想・推測を足さない。

## 10. 振る舞いを変えるときの手順

1. 変更が「やる / やらない」なら `vision.md`、「振る舞い」なら `specs/`、「なぜ」なら `decisions/` を直す。迷ったら 1. の表に戻る。
2. 直した事実が `README.md` の「一次情報」表に無ければ 1 行足す。
3. 他の文書に同じ事実の再掲が無いか探し、あればリンクに置き換える。
4. 決められないことが残れば OQ を起票する。解決した OQ は「解決済み」へ移して決定へリンクする。
5. **docs を先に書いてコミットし、そのあとコードを書く。** 同じ PR で出す。「docs は後で」にしない。
6. PR 作成前に `/check-docs` を回す。

## 11. 最初に敷く最小構成

新しいリポジトリでは、次だけ作れば回り始める。骨組みは雛形にあり、中身は人が書く。

```
docs/
├── README.md             # 一覧と役割・読む順番・一次情報は 1 か所の表
├── vision.md             # 誰のため・責務・やること・やらないこと・判断の基準
├── workflow.md           # Issue → PR の進め方(正)
├── open-questions.md     # OQ-NNN のハブ
├── specs/
│   ├── README.md         # 書き方・状態・一覧・予定
│   └── _template.md
└── decisions/
    └── _template.md
```

最初の決定は「テスト戦略」と「ディレクトリ構成」になることが多い。これを `D-0001` `D-0002` として書き、`README.md` の表と `AGENTS.md` の「コードを書くとき」に番号を入れると、以後の Issue が参照できる。
