# 開発の進め方

Issue から PR までの進め方と、仕様とコードをそろえるための決まり。人が作業するときも AI が作業するときも同じ決まりに従う。AI 向けの要約は `AGENTS.md` にあるが、正はこの文書。

## 基本の考え方

- **Issue 駆動**: 作業は必ず Issue から始める。1 つの Issue は 1 つの機能か 1 つの作業にし、1 Issue = 1 ブランチ = 1 PR にする。
- **docs が先**: 1 つの PR の中で、仕様・未解決の項目・決定を先に書き、そのあとでコードを書く。
- **仕様駆動**: `specs/` の仕様とコードは、どの時点でも食い違わせない。

## 作業の流れ

### 1. Issue を立てる

- `.github/ISSUE_TEMPLATE/` のテンプレート(機能実装 / バグ報告 / 設計議論)で書く。Claude Code では `/create-issue <一文>` が質問で詳細を掘って起票する。
- 1 つの Issue に複数の機能を入れない。大きい機能は、独立して PR にできる単位に分ける。
- `vision.md`「やらないこと」に当たらないかを確かめる。当たるなら、先に `vision.md` を書き換える合意を取る。

### 2. ブランチを作る

- ブランチ名は `feat/<Issue 番号>-<短い英語の名前>`。バグは `fix/`、docs だけなら `docs/`、それ以外は `chore/`。
- `main` に直接コミットしない。

### 3. docs を書く

コードを書く前に、次の順に書いてコミットする。

1. `specs/` の該当する仕様を書くか、書き換える。新しい機能なら `specs/_template.md` を写す。受け入れ条件を確定させ、状態を「合意」にする。
2. 書いている途中で決められないことが出たら、`open-questions.md` に OQ を起票する。
3. 何かを決めたら、`decisions/` に記録を追記する(`/record-decision`)。
4. `vision.md` に関わる変更なら、`vision.md` も書き換える。

実装に必要な項目が未解決のままなら、**推測で決めて実装に進まない**。Issue か PR で決める人に尋ね、決まってから進む。

### 4. コードを書く

- 仕様に書いた振る舞いだけを実装する。仕様に無い振る舞いが要ると分かったら、先に仕様に書き足す。
- 計算・判定のロジックは純粋関数に切り出し、ロジックテストを書く。テストは仕様の受け入れ条件と対応させる。
- 画面が変わる変更では、関係する E2E のフローを流す。範囲の決まりはテスト戦略の決定(`decisions/`)を正とする。

### 5. PR を出す

- `.github/pull_request_template.md` の形で書く。本文に `Closes #<Issue 番号>` を書き、「ドキュメント」欄に書き換えた仕様・OQ・決定を書く。
- PR タイトルは `feat: 〇〇を追加` の形式(`feat:` `fix:` `docs:` `chore:` + 日本語)。**squash merge でそのまま main のコミットメッセージになる。**
- テスト・lint・typecheck を通してから出す。落ちたまま PR を作らない。
- 受け入れ条件を 1 つずつ確かめ、満たしたものにだけチェックを付ける。全部満たしたら仕様の状態を「実装済み」にする。

### 6. レビューしてマージする

- 仕様とコードが食い違っていないかを確かめる。
- この PR で解決した OQ が「解決済み」になり、決定へリンクしているかを確かめる。
- **squash merge** する。`commit_title` は `<PR タイトル> (#<PR 番号>)`、本文は空にする。Claude Code では `/merge-pr` がチェックとマージと後片付けを行う。

## 仕様とコードをそろえる決まり

- コードの振る舞いを変える PR では、同じ PR で仕様も書き換える。仕様だけ、またはコードだけを変える PR はマージしない。
- docs だけを変える PR(誤字の修正、OQ の追記、決定の記録など)はマージしてよい。
- 仕様とコードの食い違いを見つけたら、どちらに合わせるかが決まるまで OQ に書く。決まったら、合わせる側を直す PR を出す。
- リファクタリングのように振る舞いを変えない PR では、仕様を変えなくてよい。PR の「ドキュメント」欄に「変更なし」とその理由を書く。

## AI が作業するとき

- 作業を始める前に `docs/README.md` の「読む順番」に従って読む。
- Issue の範囲を超える変更はしない。範囲の外で直したほうがよいものを見つけたら、新しい Issue の案として報告する。
- 決めるべきことを自分で決めない。選択肢と推奨を添えて OQ に書き、尋ねる。
- `decisions/` の既存のファイルを消したり、本文を書き換えたりしない。
