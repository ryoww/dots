# 仕様

機能ごとの仕様を置く。コードはここに書いた振る舞いに合わせる。

## 書き方

- 1 つの機能に 1 つのファイルを作る。ファイル名は短い英語にする(例: `room-create.md`)。他の文書からは `specs/room-create.md` の形で参照する。
- 新しく作るときは `_template.md` を写す。
- 仕様には**何がどう振る舞うか**を書く。**なぜそう決めたか**は `decisions/` に書き、仕様からは `D-XXXX` でリンクする。
- 決まっていないことは推測で書かず、「未確定(`OQ-NNN`)」と書いて `open-questions.md` の項目へリンクする。
- 受け入れ条件は、満たしたかどうかを人が確かめられる形で書く。テストはこの条件と対応させる。

## 状態

各仕様の冒頭に、次のどれかを書く。この一覧の「状態」列は各仕様の冒頭を写したもので、**正は各仕様のファイル**。ずれていたら一覧を直す(`/check-docs` が検査する)。

- **下書き**: 書いている途中。未解決の項目が残っている。
- **合意**: 内容が決まり、実装してよい。
- **実装済み**: コードがこの仕様どおりに動く。受け入れ条件がすべてチェックされている。

## 一覧

| 仕様 | 状態 | Issue |
|---|---|---|
| (`<機能>.md` 機能の名前) | 下書き | #番号 |

## 予定(仕様がまだ無い機能)

完成形には含まれるが、仕様も実装もまだ無いもの。**ここに載っている機能のコードは存在しない。** 着手するとき Issue を立て、仕様を作ってから上の一覧へ移す。「作らない」と決めたものはここではなく `vision.md`「やらないこと」に書く。

| 機能 | 着手するときの注意 |
|---|---|
| (機能の一文) | (先に決めること。決定が要る・OQ の確定が要る・基盤の導入が要る等) |
