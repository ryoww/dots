`docs/` 全体の整合性を検査し、結果を報告する。**修正はユーザーの承認を得てから**行う。

## 検査項目

1. **リンク・参照**: docs 内の相対リンクや、`D-XXXX`・`OQ-NNN`・`specs/xxx.md`・`vision.md` 形式の参照が、実在するファイル・項目を指しているか。
2. **目次との一致**: `docs/README.md` の目次と「一次情報は 1 か所」の表が指す文書・パスが実在するか。`docs/` にあるのに README のどの行からも辿れない文書は無いか。
3. **一次情報の重複**: `docs/README.md`「一次情報は 1 か所」の表に載っている事実が、正とされる文書以外で再定義(リンクではなく再掲)されていないか。
4. **仕様の状態**:
   - 各 `specs/*.md` の冒頭の状態と、`specs/README.md` 一覧の状態が一致しているか。
   - 状態が「実装済み」の仕様の受け入れ条件に、未チェックが残っていないか。
   - 状態が「下書き」なのに、未解決の項目が「なし」になっていないか。
5. **決定の健全性**:
   - `docs/decisions/` の番号が連続し、**重複が無い**か(並行する PR で同じ番号が入ることがある)。
   - 「置き換える記録」の参照先が実在するか。置き換えられた記録(メタ行の直後に「この記録は D-XXXX で置き換えられた」の注記がある記録)を、正として参照している箇所が無いか。
   - 既存の記録の本文が、git 履歴で書き換えられていないか(`git log -p -- docs/decisions/` で確認できる範囲で。置き換えの注記の追加は除く)。
6. **未解決の項目**:
   - 本文で「未確定」「OQ-NNN」と参照している ID が、`docs/open-questions.md` に実在するか。
   - 「解決済み」の項目が決定(`D-XXXX`)へリンクしているか。
   - 「未解決」のままなのに、解決する決定が存在する項目が無いか。
   - 番号の使い回しが無いか。
7. **vision との整合**: `vision.md`「やらないこと」に当たる仕様が無いか。
8. **コードとの乖離**(アプリのソースが存在する場合のみ):
   - 構成・依存ルールを定めた決定があれば、その違反が無いか。
   - 状態が「実装済み」の仕様に対応するコードが実在するか。
   - スキーマの正とされる場所(`docs/README.md` の表で確認)の実スキーマと、設計の記述が矛盾していないか。

## 報告形式

- 問題を「**重要**(事実の矛盾・リンク切れ・ルール違反)」と「**軽微**(表記ゆれ・目次の抜け)」に分けて列挙する。
- それぞれ該当ファイルと行、修正案を添える。
- 問題がなければ「問題なし」と明確に報告する。検査した項目の一覧も添える。
