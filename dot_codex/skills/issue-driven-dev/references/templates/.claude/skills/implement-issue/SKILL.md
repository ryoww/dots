Issue 駆動開発の実装フェーズを実行する。対象 Issue: $ARGUMENTS

GitHub の操作は GitHub MCP ツール(リポジトリ: `{{REPO}}`)で行う。gh CLI がインストールされていれば同等の gh コマンドでもよい。

進め方の正は `docs/workflow.md`。1 つの PR の中では、**docs を先に書き、そのあとコードを書く**(仕様 → OQ → 決定 → 実装)。

## 手順

### 1. Issue の理解

1. GitHub MCP の `issue_read` で Issue の本文とコメントを読む。
2. Issue に書かれた仕様(`docs/specs/`)・OQ・決定を必ず読む。書かれていなければ `docs/README.md` の読む順番で該当文書を探して読む。
3. 受け入れ条件が曖昧、または仕様・`docs/vision.md` と矛盾している場合は、実装を始める前にユーザーに質問する。

### 2. ブランチ作成

1. 作業ツリーがクリーンであることを確認する。未コミットの変更があれば停止してユーザーに確認する。
2. `git checkout main && git pull` で最新化する。
3. ブランチを切る。命名: `feat/<番号>-<英語スラッグ>`(機能)、`fix/<番号>-…`(バグ)、`docs/<番号>-…`(ドキュメント)、`chore/<番号>-…`(その他)。

### 3. ドキュメントを書く

1. `docs/specs/` の仕様を書くか書き換える。
   - 新規の仕様は `docs/specs/_template.md` を写す。状態は「合意」にして、受け入れ条件を確定させる。
   - 決められないことが出たら、推測で決めず `docs/open-questions.md` に OQ を起票する。**実装に進まず、ユーザーに尋ねる。**
2. 決めたことは `/record-decision` の形式で `docs/decisions/` に追記する。
3. ここまでを先にコミットする(コード変更と分ける)。

### 4. 実装する

- `AGENTS.md` と関連する決定の規約(依存方向・配置・テスト戦略)に従う。
- 仕様に書いた振る舞いだけを実装する。仕様に無い振る舞いが要ると分かったら、先に仕様へ書き足してから実装する。
- 計算・判定ロジックは純粋関数に切り出し、{{LOGIC_TEST_TOOL}} テストを書く(テスト戦略の決定)。テストは仕様の受け入れ条件と対応させる。

### 5. 検証

- テスト・lint・typecheck を実行して全て通す(存在するもののみ)。
- 画面が変わる変更(新機能・UI に触れる fix)では、関係する E2E({{E2E_TOOL}})のフローを流す。無ければ追加する。流したフローと成否は PR 本文の表に書く(テスト戦略の決定)。ロジックだけ・docs だけの変更では流さない。
- Issue の「全体リグレッションが要る」にチェックがあれば、全フローと手動チェックリストを確認し、結果表を PR 本文に貼る。
- 仕様の受け入れ条件を 1 つずつ確かめ、満たしたものにチェックを付ける。確かめていないものにチェックを付けない。全部満たしたら仕様の状態を「実装済み」にする。
- 結果を正直に報告する。落ちたまま PR を作らない。

### 6. PR 作成

1. コミットして push する。コミットメッセージは日本語で `feat:` 等のプレフィックス付き。
2. `.github/pull_request_template.md` の構成に従って PR 本文を書き、GitHub MCP の `create_pull_request` で PR を作成する。
   - タイトル: `feat: 〇〇を追加` の形式(squash merge でそのまま main のコミットメッセージになる)。
   - 本文に `Closes #<番号>` を必ず入れる。
   - 「ドキュメント」欄(仕様・OQ・決定)を埋める。変更が無い項目は「変更なし」と書く。
3. PR の URL と、受け入れ条件それぞれの達成状況を報告する。

## してはいけないこと

1. main に直接コミットする。
2. マージまで勝手に行う。ユーザーの指示があった場合のみ、GitHub MCP の `merge_pull_request`(merge_method: squash)で行う。
3. Issue に書かれていない機能を勝手に足す。気づきがあれば PR 本文への記載や新しい Issue(/create-issue)で提案する。
4. OQ が未解決のまま推測で実装する。
5. `docs/decisions/` の既存ファイルを消す、または本文を書き換える。覆すときは新しい記録を書く(`/record-decision`)。
